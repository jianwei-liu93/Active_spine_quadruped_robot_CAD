# r15 verification reuse plan

## Scope and starting evidence

This is a read-only reuse audit for a small r15 source-geometry change, with the lumbar frame as the most likely candidate. It does not certify any r15 geometry. The inspected r14 checkpoint is `cad/flexor_r14_robot.FCStd`, SHA-256 `7e4d8fbf239bde96e9ef63c4cdbe3001427e37b1358739cc3a2a0a990610eb87`; its accepted inventory is 455 physical `App::Link` instances and 108 used source definitions. The STEP round trip recorded 455 valid solids and STEP SHA-256 `c76607167ddab759f1560d21a82032aee877a64b3b95e3f187eacb7de09ce7f9`. Native checks report saved reopen/recompute and reversible feature-edit/restore pass. The motion report is explicitly `PASS_AFFECTED_FINITE_ONLY`: 91 inclusive spine phases at 4 degrees with stored neutral legs and wheel zero, and 32,032 affected unordered pairs. It is finite pose evidence, not continuous-clearance evidence.

The AX0/AX1 record is `animation/motion/ax01_r14.json`; it binds the native, r14 parameter file, candidate parameter file and `PoseController.MotionMap`, with 455 instance IDs and 108 source meshes. The production/presentation products in `animation/motion/production_coordination_r14.json` and the Blender scene, video, reports and view captures are r14 evidence. Preserve the complete r14 source/dependency hash sets as well: `reports/verification/r14_motion_91.json` records 43 native/config/manifest/helper inputs in `dependency_sha256`, while `reports/animation/ax01_r14.json` binds the AX0 exporter, grounding file and seven procedural generator sources. Keep those files and their hash-bound sources unchanged. In particular, don't point new reports at old outputs or alter an r14 script/report to say r15.

The likely one-source candidate is `FRM_LUMBAR_COMPACT_CAGE_r12`, generated by `src/spine_frame_r12.py` (`frame_parameters`, `build`; source name at line 13) and attached to `LumbarIntegrated1`. The r14 AX0 manifest confirms this exact source-instance association. If that stays the only geometry change, preserve all 455 instance names, all 108 source names, all placements/local frames and MotionMap entries; only the source BRep/feature values and its new geometry hash should change. `src/build_robot_r14.py` is not a safe r15 entrypoint as-is: `finalize` and `from_checkpoint` write fixed r14 paths/configuration and carry r14 naming. Make r15-owned copies/wrappers and have the lead integrate into a separately saved r15 document via the installed FreeCAD MCP.

## Smallest defensible verification path

1. **Freeze the baseline and identify changed identities.** Record SHA-256 for the r14 FCStd, parameters, AX0 manifest, r14 identity/motion/STEP/native reports, STEP file, and every reused verifier/adapter source. In the new r15 identity report, compare the saved r15 native to the saved r14 native by exact App::Link name, `LinkedObject.Name`/PartNumber, source-local placement, link placement, numeric feature properties, and BRep identity. Add a physical instance to the changed set whenever its linked source BRep or identity changed; expand a changed source to every physical instance that references it. Record new and retired IDs separately and fail if any are unexpected. For the one-lumbar-source case, the expected changed instance set is `{"LumbarIntegrated1"}` and expected new/retired sets are empty. Preserve the 455/108 inventory and identity order.

2. **Reopen, recompute and inspect the r15 native.** Extend the behavior of `src/check_native_r14.py:run` in a new r15 checker: open the saved r15 file in a disposable document, force recompute, walk every PartDesign Body and member state, require every sketch fully constrained, and require each used source Body valid with exactly one solid and no feature error. Probe one or two relevant editable parameters on a disposable copy of the revised source, recompute, observe a real geometry change, restore the values and prove BRep identity; never overwrite the r14 native or test by changing the canonical r15 doc. Compare source datums, placements and critical interface sketches against r14; ensure pivot, bearing, guide, mounting and motor coordinates remain equal. Also record changed-source volume, bbox, mass estimate and section metrics. These checks are revision specific even if the instance identities are reused.

3. **Run a new changed-pair screen.** Reuse the detached-shape/finite-pose approach of `src/animation_coordination_screen_r14.py:run`, `src/verify_compact_revision_r12.py:prepare/run`, and the pair uniqueness idea in `src/verify_changed_revision_r10.py:affected_pairs`; do not call the r14 entrypoint unchanged. Generate the r15 changed set from the identity/BRep comparison above rather than copying the r14 fixed 77-ID set. For `N=455` and one changed ID, screen `N-1=454` unique unordered changed-versus-all pairs per phase; generally the count is `d*(N-d)+d*(d-1)/2`, where `d` is the number of changed/added IDs after excluding retired IDs. Use the candidate's r15 descriptor and actual copied world shapes; verify shape coverage equals the exact current App::Link set and regenerate every requested spring/cable shape. Use the 91-phase neutral-leg 0..360-degree/4-degree grid as the low-cost spine-cycle screen. Additionally inspect a small declared coordinated-motion subset (cycle start, quarter, half, three-quarter and endpoint, with actual current r14 prescribed spine/leg/wheel trajectory values) for changed-frame pairs and nearby leg/cable pairs. If a changed component is near a cable/spring owner or travel envelope, include its full attached dependency neighborhood at those samples. Report bbox exclusions and OCC checks separately, with actual intersection volume threshold and pair/sample ledgers. Any finite result remains finite-sample evidence only.

4. **Export and round trip r15 STEP.** Adapt `src/export_assembly_r14.py:run` in a new file. Export the 455 intended App::Links to `exports/step/r15/flexor_r15_robot.step`, reload it, require valid geometry and exactly 455 solids, then compare each STEP solid against its corresponding native world shape with the established strict geometry/volume/bbox checks from `src/verify_frame_revision_r09.py:_strict_shape_identity` / `adaptive_volume_r07.validate_solids`. Bind the report to both native and STEP hashes and guard that the open native snapshot and file hash did not change. The r14 exporter writes a fixed r14 directory/report and must not be run unmodified for r15.

5. **Regenerate AX0/AX1 with a thin r15 adapter.** `src/animation_pose_export.py:run` is the best reusable AX0 core: it reads actual App::Links and MotionMap, hashes source-local BReps, checks copied-shape placements and datum reprojection, and emits stable `instance:` IDs, source `mesh:` IDs and frame samples. A fresh r15 wrapper should select `cad/flexor_r15_robot.FCStd`, `parameters/assembly_r15.json`, `animation/schema/grounded_instances_r15.json`, output `animation/motion/ax01_r15.json` and `reports/animation/ax01_r15.json`, while requiring exact expected paths/revision, stable 455/108 inventory, identity source/shape placements, no unsupported LinkTransform/scale, and explicit r14-to-r15 changed source hashes. Do not copy old `cad_sha256`, `parameter_files_sha256`, MotionMap SHA or mesh hashes. The r15 grounded-instance file must be versioned and bound to the r15 CAD hash even if its names are unchanged.

   `src/animation_production_export.py:run` can extend the r15 AX0 to local rigid meshes and prescribed streams; `animation_production_validate.py:validate` checks those hashes and frame mappings. Both are revision-derived internally, but should be invoked only after an r15 AX0 report exists and through a copied r15 wrapper that records its own dependency hashes. The full exporter writes 15 s and 20 s, 60 fps timelines, so it is more than needed for a small interoperability preview. To keep the preview bounded, add a separate r15 preview wrapper that derives five to nine selected frames directly from the current accepted trajectory and `leg_motion_r07.descriptor`, exports only the changed source mesh plus its current source-local transforms (and nearby unchanged meshes needed for context), and stores trajectory/input and mesh SHA-256. For a whole-robot context view, reuse unchanged r14 source-local meshes only after validating each source hash against the r14 manifest, and use the selected r15 transforms for all instances. Re-export the changed source from r15; never show the r14 mesh for the changed instance. Preserve mm-to-m, right-handed axes, neutral local geometry and one placement application. Label the clip as a prescribed-kinematic preview, not a dynamics or clearance proof.

## Blender preview boundary

The existing Blender scripts are bound tightly to r14: `animation/blender/build_coordination_s2_r14.py:build` assumes the r14 scene, 455 instances, 108 sources, r14 production manifest, r14 timeline and r14 presentation configuration; `animation/blender/verify_coordination_s2_r14.py:run` checks the same r14 literals. Do not change those expectations or rebuild the 25-second video for this geometry change. Create a small r15 preview scene with the installed Blender MCP (`execute_blender_code` for scene construction and `get_scene_info`/`look` for inspection). Import the small r15 preview payload, confirm changed-mesh hash/source ID and instance mapping, then capture only selected frames in a new scene/report such as `animation/blender/r15_geometry_preview.py` and `reports/animation/r15_geometry_preview.json`. The already recorded MCP inventory identifies `execute_blender_code`, `get_scene_info` and `look`; the lead should confirm live Blender availability when doing the authorized preview. Do not use an AI generated mesh or edit the r14 scene.

## Evidence limits and reusable invariants

Reused evidence can cover unchanged source geometry, instance identity, mechanism graph and poses only when the new r15 identity proof shows the relevant inputs are byte/geometry identical and the r15 parameters and MotionMap preserve their motion numerics. It cannot cover the changed source's fit, strength, mass, clearance, STEP round trip, mesh, or visual appearance. AX0/AX1 must be regenerated because source hashes change. The old r14 STEP is a baseline reference, not the r15 export. A finite screen cannot establish continuous clearance; section screening is not structural qualification; the source morphology is not dimensionally exact; and the prescribed leg/cable animation is not loaded dynamics. Keep each statement in the r15 report bounded to what its new evidence actually checks.
